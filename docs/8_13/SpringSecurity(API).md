permitAll()(認可)とCSRF保護は、会社の「受付」と「本人確認」くらい別物、というイメージです

permitAll()って何だったか

これは「この入り口(URL)は、社員証(ログイン)を見せなくても通っていいですよ」という受付のルールです。/products/syncをpermitAll()にしたのは、「Dellという外部の会社が来る入り口だから、社員証(ログイン)は求めない」という設定でした。

CSRFって何か

これは受付とは全く別の**「本人確認の紙」**のようなものです。Spring Securityは、POSTのようなデータを書き換えるリクエストに対して、デフォルトで「この紙(トークン)を一緒に持ってきてね」と要求します。

なぜこんな仕組みがあるかというと、普段ブラウザでログインしている人が、悪意あるサイトに騙されて、知らないうちに自分のアカウントで勝手な操作(送金など)をさせられてしまう、という攻撃(CSRF攻撃)を防ぐためです。ブラウザ経由の操作にはこの「紙」を毎回発行してチェックする、というのが標準の動きです。

今回何が起きていたか

受付(permitAll())は「Dellさん、社員証なしでどうぞ」と通した
でも警備員(CSRFチェック)が別にいて、「その紙(トークン)持ってないですよね? 通せません」と止めていた

つまり2つの別々の門番がいて、片方だけ突破しても、もう片方に止められていた、という状況でした。

なぜこれがDellのようなサーバー間通信で問題になるか

CSRFの「紙」は、そもそも人間がブラウザでログインしたときに発行されるものです。Dellのプログラムは人間のようにログインもブラウザ操作もしていないので、そもそもこの「紙」を持ちようがありません。なので、**「Dellのような、プログラム同士の通信では、この紙のチェック自体を免除してあげる」**という設定(csrf.ignoringRequestMatchers("/products/sync"))が必要だった、というわけです。

まとめると、「誰でも入っていい入り口にする」のと「入るときの手続きを省略する」は別の話で、両方を許可して初めて通れる、というのが今回の教訓でした。
